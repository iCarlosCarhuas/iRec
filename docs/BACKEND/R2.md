# Cloudflare R2 — BYO Storage

## Estado

Target: `v0.4.0 — R2 + Photos`.

`ADR-0003` mantiene la decisión base: cada creador conecta su propio Cloudflare
R2. R2-0 fijó el modelo y lifecycle; R2-1 introdujo `StorageConnection` y la
persistencia cifrada. R2-2 incorpora el cliente S3-compatible y la verificación
real del bucket antes de persistir o actualizar `last_verified_at`.

## Principio BYO

- el creator/owner conserva el bucket dentro de su cuenta Cloudflare;
- iRec no se convierte en dueño del almacenamiento;
- el navegador nunca recibe Secret Access Key;
- credenciales R2 no se guardan en localStorage/sessionStorage;
- credenciales no deben aparecer en logs, documentación ni Git;
- secretos reversibles se cifran server-side con el `CryptoService` existente.

## StorageConnection

La conexión pertenece al usuario/owner y puede reutilizarse entre álbumes.

Modelo de source introducido en R2-1:

```text
storage_connections
├── id
├── owner_id
├── account_id
├── bucket
├── access_key_id_encrypted
├── secret_access_key_encrypted
├── last_verified_at
├── created_at
└── updated_at
```

`albums.storage_connection_id` es nullable en el source de R2-1. De esta forma los
álbumes existentes de v0.3.0 siguen siendo válidos sin almacenamiento R2. El FK
usa `ON DELETE SET NULL` para no borrar álbumes al retirar una conexión.

## Flujo de conexión

El owner proporciona:

- Account ID;
- bucket;
- Access Key ID;
- Secret Access Key.

Flujo congelado entre R2-1 y R2-2:

1. API recibe credenciales solo sobre HTTPS y requiere sesión;
2. R2-2 construye el endpoint S3-compatible y prueba permisos mínimos;
3. solo si la validación R2 pasa, llama al boundary interno de R2-1;
4. R2-1 cifra Access Key ID y Secret Access Key con `CryptoService`;
5. persiste la conexión con `last_verified_at`;
6. los contratos de salida nunca contienen credenciales.

R2-2 expone:

```text
POST /storage-connections
GET  /storage-connections
POST /storage-connections/:connectionId/test
```

`POST` verifica primero con `HeadBucket` usando el endpoint estándar
`https://<ACCOUNT_ID>.r2.cloudflarestorage.com` y `region=auto`; solo después llama
a `persistVerified()`. El test de una conexión descifra las credenciales
server-side, vuelve a verificar R2 y actualiza `last_verified_at`.

La API limita llamadas de verificación por usuario/IP y nunca devuelve Access Key
ID ni Secret Access Key. R2-2 cubre buckets de jurisdicción `default`; endpoints
jurisdiccionales específicos quedan para una extensión posterior si el producto
los necesita.

## Photo assets

Las fotografías son un dominio separado de `album_proposals`.

`album_proposals` continúa representando exclusivamente propuestas textuales de
v0.3.0.

Modelo conceptual:

```text
album_assets
├── id
├── album_id
├── storage_connection_id
├── uploaded_by
├── object_key
├── thumbnail_object_key       nullable
├── original_filename
├── mime_type
├── size_bytes
├── width                      nullable
├── height                     nullable
├── checksum                   nullable
├── status
├── uploaded_at                nullable
├── moderated_by               nullable
├── moderated_at               nullable
├── created_at
└── updated_at
```

Estados de moderación:

```text
pending
approved
rejected
```

`uploaded_at = NULL` puede representar un asset reservado cuyo upload aún no fue
confirmado; no se añade otro state machine en R2-0.

## Autorización prevista

```text
owner
  upload -> approved
  list   -> todos los assets del álbum
  moderate -> pending assets
  delete -> permitido con validaciones

active member
  upload -> pending
  list   -> aprobados + sus propios assets según contrato final
  moderate -> no

invited / removed
  upload -> no

anonymous
  upload -> no
  read -> approved solamente cuando album.visibility = public
```

Las funciones de policy existentes de Album Core se reutilizarán o extenderán en
una capa testeable; no se duplicará autorización dentro de controllers.

## Upload directo

Flujo objetivo:

1. PWA solicita autorización/presign para un álbum;
2. API valida sesión, álbum, membership y storage connection;
3. API reserva/define el asset y crea un object key controlado;
4. API devuelve una URL prefirmada de corta duración;
5. navegador sube directamente a R2;
6. PWA confirma finalización;
7. backend verifica el objeto/metadata antes de considerar el upload completado;
8. PostgreSQL conserva metadata, ownership y estado de moderación.

Los bytes de la imagen no deben atravesar normalmente el NestJS API.

## Namespace

```text
albums/{albumId}/originals/{assetId}.{ext}
albums/{albumId}/derived/{assetId}/thumb.webp
albums/{albumId}/themes/{themeId}/...
```

El cliente nunca define libremente el prefijo final ni un object key arbitrario.

## Lectura

Los buckets no necesitan hacerse públicos para cumplir el MVP.

La estrategia prevista es lectura autorizada mediante URLs prefirmadas de corta
duración. El contrato y expiración exactos se fijarán al implementar R2-5.

## Delete

Eliminar metadata de PostgreSQL y eliminar un objeto de R2 son side effects
separados. R2-5 deberá definir explícitamente orden, error handling y recuperación
parcial antes de implementar delete.

Nunca se borrará un bucket como parte de borrar una foto o álbum.

## CORS

La configuración debe limitar los orígenes necesarios para la PWA y los métodos
requeridos por el upload directo. La documentación final debe guiar al owner sin
exponer credenciales.
