# iRec v0.3.0 — Runtime / E2E Gate

Este gate valida el flujo completo de **Identity + Album Core** antes de crear
el tag `v0.3.0`.

No requiere crear migraciones nuevas. No usar `down -v`, `volume rm`,
`prune --volumes` ni restore de PostgreSQL durante este gate.

## 1. Runtime base

```bash
docker compose up -d --build \
  irec-postgres \
  irec-redis \
  irec-mailpit \
  irec-api \
  irec-web

docker compose ps -a
```

Esperado:

- `irec-postgres`: healthy
- `irec-redis`: healthy
- `irec-mailpit`: healthy
- `irec-api`: healthy
- `irec-web`: healthy
- `irec-migrate`: `Exited (0)` es correcto

Smoke:

```bash
BASE_API="http:""//127.0.0.1:3000"
BASE_WEB="http:""//127.0.0.1:4200"

curl -sS -o /dev/null -w "API READY: %{http_code}\n" \
  "$BASE_API/api/health/ready"

curl -sS -o /dev/null -w "WEB ROOT: %{http_code}\n" \
  "$BASE_WEB/"

curl -sS -o /dev/null -w "PUBLIC SPA: %{http_code}\n" \
  "$BASE_WEB/a/00000000-0000-4000-8000-000000000000"
```

Los tres deben responder `200`.

## 2. Owner

Usar una cuenta owner existente.

Validar desde `/albums`:

- lista de álbumes accesible;
- creación de álbum funcional;
- detalle del álbum accesible;
- edición de título, descripción y visibilidad;
- roster de miembros visible;
- invitación de un usuario verificado;
- owner no puede eliminarse a sí mismo;
- propuestas visibles;
- owner puede aprobar o rechazar una propuesta `pending`.

Las escrituras de este bloque son persistentes. Para el release gate se
recomienda reutilizar un álbum de smoke existente y no hacer limpieza
destructiva.

## 3. Member

Usar un miembro `active` distinto del owner.

Validar:

- el álbum aparece en `/albums`;
- puede abrir el detalle de un álbum privado donde es miembro activo;
- puede ver el roster permitido;
- no ve controles de edición del álbum;
- no puede invitar/remover miembros;
- no puede moderar propuestas;
- puede crear una propuesta;
- la propuesta queda `pending`.

## 4. Moderación

Volver como owner:

- la propuesta creada por el member aparece `pending`;
- aprobarla desde la UI;
- confirmar que queda `approved`;
- confirmar `moderated_by` y `moderated_at`.

No cambiar luego la decisión al estado opuesto.

## 5. Public / Private / inexistente

Usar un álbum de smoke y recordar su visibilidad original.

Como owner:

1. cambiar temporalmente a `public`;
2. abrir `/a/:albumId` en incógnito sin sesión;
3. confirmar título y descripción;
4. confirmar ausencia de miembros, propuestas y controles administrativos;
5. devolver el álbum a su visibilidad original.

Para un álbum `private`, `/a/:albumId` debe mostrar un estado genérico
`Álbum no disponible`.

Repetir con un UUID inexistente. El estado visible debe ser equivalente al de
un álbum privado y no debe revelar título, descripción, owner ni membresías.

## 6. Evidencia final

Antes del release guardar en la conversación/sesión de QA:

```bash
git status
git log -8 --oneline

docker compose ps -a

docker exec irec-postgres psql \
  -U irec \
  -d irec \
  -c "SELECT id, title, visibility FROM albums ORDER BY created_at DESC LIMIT 10;"
```

Y registrar:

- owner flow: PASS
- member flow: PASS
- proposal flow: PASS
- moderation flow: PASS
- anonymous public flow: PASS
- private/nonexistent isolation: PASS
- source/release gate: PASS

Solo después de estos PASS se crea el tag `v0.3.0`.
